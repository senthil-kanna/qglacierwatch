01The big picture

QGlacierWatch forecasts how much water will flow in the Beas River 1, 7 and 30 days ahead. Instead of a single number it gives a range: a low value (P10), a middle value (P50) and a high value (P90). Around that forecasting model, the project builds the "operations" machinery that keeps a model trustworthy after it is deployed. That machinery is called MLOps (machine learning operations).

In one sentence: collect data automatically, check it, train and test models fairly, only allow a model into use if it passes strict checks and a human approves, watch for changes in the data, retrain when needed, and serve the forecasts through an API and a dashboard, ready to run on the Azure cloud.

Two extra research modules sit beside the main pipeline: a quantum versus classical model comparison, and glacial lake mapping from satellite images.

02The river and the problem

The Beas above Bhuntar drains a high Himalayan valley. Its water comes from three sources that change through the year: winter snow that melts in spring, glaciers that melt in summer, and monsoon rain from June to September. Floods hit the valley in July 2023. Forecasts matter for hydropower, flood preparation and water planning.

Why a model alone is not enough: a model trained once and left alone breaks quietly when seasons, weather or the input data change. Real examples from this project:

  • The uncertainty ranges were too narrow in some years and too wide in others, because each year's weather is different.
  • The river data used as the target changed its source on 2023-08-05 without any error message (chapter 9).
  • Satellite snow data has gaps on cloudy days.

MLOps is the answer to these problems: checks, versioning, monitoring, governance and repeatable deployment.

Why GloFAS and not a real gauge? Measured daily flow at Bhuntar belongs to the Central Water Commission and is classified for Indus-basin rivers. GloFAS is a computer model of river flow, freely available. So the project predicts GloFAS, and says so everywhere.

How the data is kept trustworthy

  • Validation: every file is checked for the right columns, dates and value ranges.
  • Fingerprints: each raw file gets a SHA-256 hash, a unique fingerprint. If a file's bytes ever change, the refresh job stops instead of silently replacing data a model was trained on.
  • Versioning with DVC: big data files are versioned (like Git for data) and pushed to a remote store (DagsHub).
  • Append-only: to add 2026, the project copied the old files byte for byte and only added new days.

04From data to features

A model does not see raw files; it sees a table where each row is one day (the issue date) and each column is a feature: yesterday's flow, the last week's rain, the snow share, the temperature trend, the day of year, and so on.

The key rule is no peeking into the future. Data arrives late in real life: river flow is known a day later, MODIS a day later, ERA5-Land about 5 days later. Each feature is built only from values that would really have been available on the issue date. Breaking this rule (called leakage) makes a model look far better in tests than it will be in practice. Automated tests check for leakage.

06Uncertainty ranges: P10, P50, P90

A real forecast from the system (issued 2025-12-31, for 2026-01-07, 7 days ahead):

58.7
P10 (m3/s). Only a 10% chance the flow is lower than this.
61.4
P50 (m3/s). The middle estimate; half above, half below.
63.7
P90 (m3/s). Only a 10% chance the flow is higher than this.

So the range from P10 to P90 should contain the real value 80% of the time. That share is called coverage. If coverage is much lower than 80%, the model is over-confident (range too narrow). If it is much higher, the range is too wide to be useful. The project accepts 70% to 90%.

Conformal calibration (CQR)

Raw model ranges are usually too narrow. Conformalized quantile regression fixes this with a simple trick: run the model on a separate "calibration" period, measure how far the real values fell outside the ranges, and widen (or narrow) all future ranges by that amount. The project does this separately for each season, because monsoon errors are much bigger than winter errors.

The catch. Calibration assumes the future looks like the calibration period. In 2026 that failed: calibration used 2024-2025, which included the extreme high-flow year 2025, so ranges were widened a lot; 2026 was a calm year, so the ranges became too wide.

07Testing fairly

  1. Split by time. Train on older years, calibrate on the next years, test on the newest years. Never shuffle days, because neighbouring days are almost identical.
  2. Choose settings without the test. Model settings are chosen by rolling-origin cross-validation: train up to year X, check on year X+1, repeat for four years.
  3. Write the plan before running. Each major test has a protocol file committed to Git before any result is seen. This is called pre-registration. It stops "trying until it looks good".
  4. Score the test once. A log file records every time the test period is scored.
  5. Report failures too. Results that did not work are written up with the same care.

09The real-river check

An open telemetry gauge was found 3.7 km downstream of the outlet (Bajoura Bridge, Himachal Pradesh Water Department, published on the National Water Data Portal). Over 737 days between July 2023 and September 2026 it was compared with GloFAS and with the forecasts.

The most important finding. The forecasts are an accurate copy of GloFAS, not an accurate forecast of the real river. GloFAS itself scores NSE 0.21 against the gauge. Because the gauge's measuring method and quality are unknown, this is called a consistency check, not a validation.

Two more discoveries came from checking data sources carefully: GloFAS is reanalysis only up to 2023-08-04 and forecast-derived after that, and the gauge files may be used with credit but their raw data is not redistributed in the repository.

10Drift monitoring and retraining

Drift means the data or the model's behaviour has changed compared with what it was trained on. A weekly check looks at three things: the inputs (covariate drift), the predictions (prediction drift) and the errors once true values arrive (residual drift).

The trick is to be season-aware: comparing July with last December would always shout "drift". The season-aware detectors compare each week with the same weeks in past years.

TierTriggerAction
1Data quality problemFix the data, re-run ingestion. Model unchanged.
2Ranges driftingRecalibrate the ranges on recent data.
3Errors grow persistentlyRetrain a candidate and compare it with the current model on the same period.
4Candidate is betterPromote, only through the gate and a human approver.

11Model registry and promotion gate

Every trained model is stored with a model card: which data (dataset id), which code (Git commit), which settings and seeds, and its test scores. A model can only become the "production" model if it passes every rule of the gate:

  • NSE at least 0.7 (1 day), 0.4 (7 days), 0.0 (30 days)
  • P10-P90 coverage between 0.70 and 0.90 at every horizon
  • Better than climatology, at least 180 test samples
  • At least 2% better than the current model (if there is one)
  • A named person approves it

Every decision goes into an audit log, and rollback brings back the previous model in one command.

12Quantum benchmark

A variational quantum circuit (VQC) with 4 qubits was compared fairly with classical models of the same size (same inputs, same training budget, 5 random seeds, same calibration). It runs on a simulator, a normal computer pretending to be a quantum computer.

What to say: the simulated quantum model did not beat simple classical models on this task. A simulation can never show "quantum advantage"; the result only tells us about this model type on this problem.

13Glacial lakes

Melting glaciers can form lakes that may burst. The project maps water in the high zone (above 3,500 m, gentle slopes) every autumn from 2019 to 2025 using Sentinel-2 (optical) and Sentinel-1 (radar), tracks 34 lake objects and checks whether any grow fast.

  • Against JRC water maps the detector scores IoU 0.11-0.16 (low). It marks shadows and wet snow as water and misses lake edges.
  • A registered attempt with five improved rules found none better, so the rule stayed. A negative result, reported honestly.
  • No lake shows significant growth after correcting for testing 34 lakes at once.

20Viva questions and answers

What does your project do, in one minute?

It forecasts the Beas River's flow 1, 7 and 30 days ahead with an uncertainty range, using satellite snow cover and weather data. Around the model it has a full MLOps pipeline: versioned data, fair testing, a model registry with a quality gate and human approval, season-aware drift monitoring with retraining rules, an API and a dashboard, and an Azure deployment design that costs under a dollar a month.

What is MLOps and why do you need it?

MLOps is the set of practices that keep machine learning models reliable after deployment: data versioning, automated testing, monitoring, retraining and controlled release. Without it, a model silently degrades when seasons, weather or data sources change, and nobody can tell which data and code produced a forecast.

Why GloFAS and not real gauge data?

Daily discharge for the Beas at Bhuntar is held by the Central Water Commission and is classified for Indus-basin rivers. GloFAS is an open modelled dataset. We checked it against the one open gauge we found and showed it differs a lot (NSE 0.21), so we state clearly that our skill is skill at reproducing GloFAS.

What do P10, P50 and P90 mean?

P50 is the middle estimate. There is a 10% chance the real flow is below P10 and a 10% chance it is above P90, so P10-P90 should contain the true value 80% of the time.

What is conformal calibration?

It measures how often the raw ranges missed on a separate calibration period and widens or narrows future ranges so they reach the target coverage. We do it per season because monsoon errors are larger.

Why did no model pass the gate?

The ranges were too narrow in 2023-2025 at 30 days (0.689) and too wide in 2026 (0.938 and 0.955), because calibration years and test years had very different flows. Accuracy itself was high. We report it as a finding instead of tuning until it passes.

How do you prevent cheating or leakage in testing?

Time-ordered splits, features built only from data available on the issue date, selection by cross-validation on earlier years, protocols committed before running, and a log of every test access.

What is drift, and what is special about your detector?

Drift is a change in the data or model behaviour. Normal seasons look like drift to a naive detector (it alarmed on 99.8% of weeks). Ours compares each week with the same season in past years, cutting alarms to about 5%.

Why Azure Container Apps instead of a virtual machine or Lambda?

It runs our container with the full ML libraries, scales to zero so we pay nothing when idle, gives HTTPS and revisions for rollback, and the free monthly grant covers our load. A VM would cost money all the time; Lambda-style functions limit package size.

Is the quantum model better?

No. On a simulator it was worse than linear and small neural network models. A simulation also cannot demonstrate quantum advantage; the comparison only tells us about this model type on this task.

What would you do next?

Deploy to Azure and measure cloud latency; obtain long observed discharge through an official request; try adaptive conformal methods that adjust to changing regimes; orchestrate the jobs with Durable Functions or Azure ML pipelines; improve lake mapping with labelled data and a trained model.

Did you use AI tools?

Answer honestly according to your college's rules. The report has an editable AI-assistance declaration in its acknowledgement section.
